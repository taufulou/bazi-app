## A8 — Rewarded-ad free-value vectors ✅ FIXED

Two vectors, same root cause: **V1 ads do no ad-completion verification** (`ads.service.ts` docblock: *"Trust client callback (mock ads). No server-side ad completion verification."*).

| # | Vector | Severity | Detail |
|---|---|---|---|
| 1 | `POST /api/payments/readings/:id/unlock-section` with `method: 'ad_reward'` | **MEDIUM** (downgraded from HIGH — see note) | Created a `SectionUnlock` with `creditsUsed: 0` and verified nothing — no `AdRewardLog` lookup, no SSV. (`section-unlock.service.ts:215-229`) **Severity note:** the original HIGH rating assumed unlock rows control content access. They do not — `SectionUnlock` is read by nothing on the delivery path (F3), and an owner already receives every section in full (F2). So this closes a *credit-avoidance / row-creation* path, not a content-access path. The mirror-image problem is that the surviving `credit` method debits real credits for a row that grants nothing — a refund liability. |
| 2 | `POST /api/ads/claim` with `rewardType: 'CREDIT'` | **HIGH** — *found during A1, not in the original plan* | **Mints real credits** (`CREDITS_PER_AD_VIEW`) to any authenticated caller with no proof an ad was shown. Bounded per account at `MAX_DAILY_AD_VIEWS = 5`/day, but Clerk signup is free ⇒ unbounded across accounts. Credits buy readings ⇒ real Anthropic spend **and** direct revenue loss (credits have a `CreditPackage.priceUsd`). |

**Blast radius before fix**: 5 credits/day/account × N throwaway accounts. At ~1–3 credits per reading and ~$0.20/reading, 100 accounts ≈ 500 credits/day ≈ $50–100/day of Anthropic spend plus the revenue never collected.

**Fix**: single kill switch `ADS_REWARDS_ENABLED` (Joi-validated `'0'|'1'`, **default `'0'`**) gating both. Verified safe: **no client CALLS `/api/ads/*` or sends `ad_reward`** in `apps/web` or `apps/mobile`, so gating is behaviour-preserving for real traffic. (Precise wording matters: `apps/web/.../InsufficientCreditsModal.tsx:113-121` does render a 「看廣告獲得 1 點」 button — but it is `disabled` with no `onClick` and constructs no URL. `apps/mobile` has no ad surface at all. Whoever wires that button up must know this flag exists.)

Design notes:
- The DTO **still accepts** `method: 'ad_reward'`. A static `@IsIn` decorator cannot be env-toggled, so rejecting there would make the flag a lie and re-enabling a code change. Enforcement lives in the service.
- In `AdsService.claimReward` the switch fires **before** the Redis daily counter, so a blocked call costs no quota and leaks no argument oracle.
- ⚠️ **Corrected** (this line previously claimed ownership resolves *before* the switch, contradicting the F3 section below and the code). `sectionUnlockEnabled()` is the **first statement** of `unlockSection` (`section-unlock.service.ts:147`), ~44 lines ahead of the ownership check at `:191` — F3 is right, this was wrong. With `SECTION_UNLOCK_ENABLED=0` (the production default) the whole method refuses before any DB read, so it leaks no existence oracle at all. The ordering claim only ever mattered in the flag-on configuration, which is not deployed. (A pre-existing 404-vs-403 split at `:144-151` distinguishes "no such reading" from "someone else's" — negligible with UUID ids, noted rather than fixed.)
- Both throw `{ code: 'ADS_REWARDS_DISABLED' }` for client branching.

**Re-enable requires BOTH**: (1) AdMob SSV wired into `claimReward` so a claim proves a real view, and (2) `unlock-section` consuming an unconsumed `AdRewardLog` row scoped to `(userId, readingId, sectionKey)` — the schema already carries those fields. Then set `ADS_REWARDS_ENABLED=1`. **Flipping the env alone re-opens both vectors** — the flag is a kill switch, not a fix.

**Tests**: 17 new (`test/ads-service.kill-switch.spec.ts` 10, `test/section-unlock-service.kill-switch.spec.ts` 7), covering default-off, both flag states, no-value-granted, check ordering, and non-regression of the credit path. The two pre-existing suites now force the flag on and say why (they test the feature, not the switch).

Mutation-tested by the line audit: deleting the ads gate fails 7/10 of its tests; deleting the unlock gate fails 4/7. **One test was found vacuous and fixed** — `'still enforces ownership'` used a negative assertion (`.rejects.not.toMatchObject(...)`, satisfied by *any* rejection) over a mock missing the `sections` wrapper, so the auditor deleted the entire ownership block and all 7 tests still passed. Now asserts `ForbiddenException` positively over a correctly-shaped mock. Ownership itself was never unprotected — `section-unlock-service.spec.ts:283,641` covers it — but the invariant this test claimed to lock was not locked.

⚠️ **Do not count `e2e/ad-rewards.spec.ts` / `e2e/section-unlock.spec.ts` as coverage**: they `fetch('/api/ads/claim')` against the *Next.js* origin, where no such route or rewrite exists, and pass purely off their own `page.route` intercepts. They could not have caught either vector and cannot catch a regression.

### F1 — ✅ RESOLVED — signup bonus was re-mintable after account deletion `[medium]`
`users.service.ts:450-464` auto-creates a user row with `credits: 3` whenever no row matches the Clerk id (a "webhook not configured" fallback), and it is reachable from most authenticated routes (`:188,196,227,267`). `deleteAccount` does **not** delete the row — it renames `clerkUserId` to `deleted_<id>_<ts>` and zeroes credits (`:113-122`). The Clerk-side delete immediately before it is best-effort: `deleteClerkUser` swallows failures (`:145-147`) and returns early when `CLERK_SECRET_KEY` is unset (`:139-142`). **If the Clerk delete fails, the Clerk identity survives while the DB row is orphaned, and the next authenticated request mints a fresh 3 credits — loopable.** Nothing gates this.
**Fixed** — and the audit undercounted the insert sites: there are **three**, not one. `ensureUser`'s fallback plus **both** `create` branches in the Clerk webhook (`handleUserCreated` and `handleUserUpdated`'s upsert). All three hardcoded `credits: 3`, so all three re-minted.

Rather than disabling the fallback (which would 404 a legitimate new user whenever the Clerk webhook lags — an availability risk at the worst moment, signup), the bonus is now **resolved once per identity** via `src/common/signup-bonus.ts::resolveSignupCredits`: it returns 0 when a soft-deleted row exists for that Clerk id (`clerkUserId LIKE 'deleted_<id>_%'`), otherwise the full bonus. The trailing underscore anchors the match so `user_ab` cannot match a deleted `user_abc`. It **fails open** on a lookup error — a database hiccup must not deny a real new user their credits, and the downside is bounded at 3.

No schema change: the `deleted_<id>_<ts>` rename already carries the fact. If a `deletedAt` column is ever added, switch the lookup and drop the prefix matching.

**Not fixed, deliberately**: the Clerk-side delete stays best-effort. `CLERK_SECRET_KEY` is Joi-`required`, so the early-return branch is dev-only, and aborting a user's account deletion because a third-party API is down is the worse failure. Consequence to accept: if the Clerk delete fails, the identity can re-authenticate and get a working (0-credit) account — deletion didn't stick, but no money is minted. Worth revisiting if account-deletion durability becomes a compliance requirement.

Tests: 6 (`test/free-spend-vectors.spec.ts`). Mutation-tested with A4a: neutering both controls fails 6/10.

### F2 — ✅ RESOLVED (owner: Option C) — reading paywall was dead code
`bazi.service.ts:541` fetches with `where: { id, userId: user.id }`, then `:554` gates on `reading.creditsUsed > 0 || reading.userId === user.id`. The second disjunct is **guaranteed true by the WHERE clause**, so `isOwnerReading` is always true, `:557` always returns early, and the preview-stripping branch at `:561-578` is unreachable. The SSE route is worse: `:621-627` emits on `if (reading.aiInterpretation)` with no payment check, and `emitStaticSections` (`:730-751`) sends `full` for every section.

**This exact bug was already found and fixed on the comparison path** — `:1293-1300` documents it verbatim ("could never be false … unreachable dead code") and switched to `paidAt !== null`, and `:813` gates on `aiInterpretation && paidAt !== null` with a comment explaining that keying on the interpretation alone "hands the full report over for free." **The reading twin and `zwds.service.ts:455` never received the fix.**

**Investigating the fix changed its shape.** Refunds fire only on outright generation failure, and the refund also nulls `aiInterpretation` — so the stream defect is not "replays stored text for free". An ungated re-stream of a refunded row runs a **full provider generation**: real Anthropic spend for a reading already refunded, and it **bypasses the 3-per-reading regeneration cap**, which is enforced in `regenerateReading`, not in the stream. That makes the stream the sharper half of F2, and a denial-of-wallet issue rather than only a content one.

**Fix shipped (Option C):**
1. **Entitlement = absence of a refund**, not presence of a charge — `!reading.refundedAt` in `bazi.service.getReading` and `zwds.service.getReading`. Deleting only the tautology was not an option: the residue `creditsUsed > 0` would paywall the 0-credit cache-hit readings F4 makes free.
2. **Stream payment gate** — `_setupStream` throws `READING_REFUNDED` on a refunded row instead of generating.
3. ~~**`regenerateReading` clears `refundedAt` AND zeroes `creditsUsed`**~~ — **REVERTED, see below.**

### ⚠️ F2 item 3 was wrong and is reverted — `regenerateReading` now touches neither field

Both the completeness and the correctness auditor independently flagged this (HIGH, confidence 82 and 90). It was a **self-inflicted regression**, not a pre-existing defect.

The reasoning behind it — "clearing `refundedAt` re-arms the refund guard, so zero the charge too" — was sound in the abstract and **unreachable in practice**. `ai.service.ts` computes ONE exclusive status per attempt: `isDegraded: true` is written only on `'degraded'` (`:1307`), `refundedAt` only on `'failed'` (`:1347`). `regenerateReading`'s WHERE requires `isDegraded: true`, so it can only ever match a row that was **charged and never refunded**. The `refundedAt: null` clear was a no-op on every row it could reach, and `creditsUsed: 0` was pure damage:

- **The user silently eats the charge.** Pay 3 → partial content → click the free retry → retry fails outright → `refundReadingCredit` short-circuits on its own `creditsUsed === 0` guard → no refund, no reading, 3 credits gone. Before this branch, that path refunded. An ordinary path with no adversary.
- **Uncapped free generation.** With `refundedAt` still null the new stream gate never fires, so every `/readings/:id/stream` re-runs a full provider generation — and `createReading` classifies the row as `isRegenerating`, handing back `streamReady` for free indefinitely, so the user cannot even create a fresh charged reading of that type.
- Paid readings render as free in web and mobile history (`creditsUsed === 0`).

**Now:** `regenerateReading` leaves `refundedAt` and `creditsUsed` alone. The double-refund it was reaching for is already prevented by `refundedAt`, which regeneration no longer clears. The refusal message was also corrected — it used to say 「請使用「重新生成」」, a path that always refuses for a refunded row; it now directs the user to create a new reading, which is what actually works.

**Lesson worth keeping:** the fix was defended by a test asserting exactly the behaviour it implemented, over a hand-built row (`creditsUsed: 0, refundedAt: null`) that the production state machine cannot produce. Reachability has to be established from the state machine, not assumed from the field names.

**Truthiness, not `=== null`.** Prisma returns `null` for an unset `DateTime?`, but a partial `select` or an incomplete mock yields `undefined`, and `undefined === null` is false — which silently paywalls **paying** customers. The strict version was written first and the zwds suite caught it: two "owner gets full content" tests flipped to preview. Locked by a `refundedAt: undefined` case.

**Tests**: 10 new (`test/reading-paywall.spec.ts`) + the zwds fixtures made realistic + the regenerate arg assertion updated. Mutation-tested: neutering both gates fails exactly the 2 tests that assert them.

### F3 — ✅ RESOLVED (owner decision: **disable**) — `SectionUnlock` rows granted nothing
The only readers of the table are `getUnlockedSections` (`section-unlock.service.ts:85`, metadata only), `getReadingWithSectionAccess` (`:283` — **called from nowhere**, verified by grep across `src/`), and admin stats (`admin.service.ts:947`). Neither `getReading` nor the stream joins it, and `apps/web` never calls `/unlocked-sections`. So the `credit` unlock method debits real credits for a row that changes nothing a user can observe.

**Owner chose (b) withdraw, 2026-08-13.** `unlockSection` now refuses behind `SECTION_UNLOCK_ENABLED` (Joi `'0'|'1'`, **default `'0'`**), checked **first — before any validation**, so a disabled deployment charges nobody and leaks no oracle (not even which section keys or reading types are valid; it never even looks the reading up). The switch **outranks `ADS_REWARDS_ENABLED`**: with the feature off, both `credit` and `ad_reward` refuse. Error code `SECTION_UNLOCK_DISABLED`.

Verified safe to disable:
- **Zero client callers** across `apps/web` + `apps/mobile` (the admin monetization page reads aggregate stats via a separate admin endpoint, which still works).
- **Zero rows in `section_unlocks`** at the time of the change (`SELECT COUNT(*), SUM(credits_used)` → `0|0|0`), so **nobody has ever paid for one — no refund liability**.
- The read path (`getUnlockedSections`) is left working; it simply returns nothing.

Re-enabling requires wiring the table into content delivery first — join `SectionUnlock` in `getReading` and `emitStaticSections`, and fix F2's dead owner-check — **then** set `SECTION_UNLOCK_ENABLED=1`. The flag alone just resumes selling the inert row.

Tests: 5 new (feature-off for both methods, charges-nothing, outranks-ads, fires-before-all-validation). Mutation-tested: neutering the gate fails **5 of 12** tests in the suite.

### F4 — ✅ NOT A DEFECT — cache reuse is **intended pricing** (owner-confirmed)
`bazi.service.ts:374-375` sets `creditsUsed = fromCache ? 0 : cost` and `:393` skips deduction on a cache hit, while `getCachedInterpretation` (`ai.service.ts:7250-7252`) keys on **`birthDataHash + readingType` with no `userId`**. So a second user with identical birth data (same date/time/city/gender) receives the full interpretation for **0 credits**. Birth data is not secret — a public figure's, or a family member's, is guessable/shareable.

**Owner confirmed 2026-08-13: intended.** *"same birth data won't charge twice, will reuse same data."* Recording the exact semantics so this isn't re-litigated or accidentally broken:

- The cache is keyed on **`birthDataHash + readingType` with no `userId`**, so reuse is **cross-user**, not just same-user. Two different accounts submitting identical birth data (date, time, city, gender) result in **one charge total** — the second is served free from the first's interpretation. This is accepted.
- ⚠️ **Binding constraint on the F2 fix**: a 0-credit cache-hit row is a *legitimate* paid-equivalent state. When A2 removes the tautological owner-check, it must **not** start treating `creditsUsed === 0` as unpaid — that would paywall exactly the readings this pricing decision says are free. Gate on an explicit paid/refunded marker (the comparison path's `paidAt !== null` pattern), never on `creditsUsed > 0`.
- Residual accepted risk, noted not actioned: birth data is guessable/shareable, so a determined user can obtain a free reading by reusing someone else's birth details. Bounded — it yields the *same* chart, not a new one — and it saves the Anthropic spend it would otherwise cost, which is the point of the cache.

## A4 — free-spend vectors ✅

### A4a — birth-profile cap ✅
`BIRTH_PROFILE_MAX_PER_USER` (Joi int ≥1, **default 10**) enforced in `createBirthProfile`, rejecting with `BIRTH_PROFILE_LIMIT_REACHED`.

⚠️ **Correction:** an earlier version of this line said a junk/negative/zero env value "falls back to 10". It does not — `Joi.number().integer().min(1)` (`app.module.ts:266`) **rejects it at boot and the app fails to start**. The `Number.isFinite(parsed) && parsed > 0 ? parsed : 10` guard in `users.service.ts` is unreachable defence-in-depth behind Joi, and the test that appears to lock it injects a mock `ConfigService`, bypassing validation entirely. Both behaviours are safe; only the documented one was wrong. The half that would matter if Joi were ever relaxed is `isFinite` — `10 >= NaN` is false, so a NaN cap would disable the control rather than fail closed.

**Deliberately not race-proof.** Two concurrent creates can both observe 9 and yield 11. "Count per user" isn't expressible as a DB constraint, overshooting by a handful is negligible against the vector, and a transaction here would serialize an ordinary user action. The per-user daily quotas (S4) are the tight bound.

### A4c — fortune free-tier scoping ✅ verified (and it reshapes A4a's rationale)
`DailyFortuneSnapshot` is `@@unique([chartHash, scope, anchorDate])`, and **`chartHash` is derived from birth data only** — date, time, city, timezone, gender — with **no `userId` or `profileId`** (`fortune-snapshot.helpers.ts::computeChartHash`).

So the free tier is *one AI narration per distinct birth chart, per scope, per day*, **shared across users** — the same cross-user cache decision as F4, applied to fortune. That means profile *count* alone doesn't multiply spend; **distinct birth data** does. An attacker gets a fresh chart just by varying the date, so the vector is real — but the cap is what bounds how many distinct charts one account can register.

**Concrete bound after A4a**: 10 profiles × 3 scopes × 1/day = **≤30 AI narrations/day per free account** (≈$1–6/day), versus unbounded before. Combined with the routes' existing 10/min throttles.

### A4b — quota SPEC (build is S4, Phase 2)
Recorded here so S4 implements rather than re-decides:

| | |
|---|---|
| Key | `quota:{userId}:{yyyymmdd}` — **day boundary in Asia/Taipei**, matching `FORTUNE_DEFAULT_TZ` and the S2 spend ledger (a UTC key resets at 8am local and produces confusing support tickets) |
| Limits (env-tunable) | readings **20/day** · chat messages **200/day** · fortune narrations **30/day** — deliberately generous; these are anti-abuse ceilings, not product limits |

| Storage | Redis `INCR` + TTL, same util as the S2 spend counters |
| Relationship to other controls | A4a caps *breadth* (how many charts), quotas cap *rate* (calls/day), S1 caps *concurrency*, S2 caps *money*. Four different axes — none substitutes for another |

## A6 — refund / clawback idempotency ✅ verified, no live defect

Every credit-returning path is reachable more than once — the AI-failure handler and the client-disconnect handler can both fire for one chat message, RevenueCat redelivers webhooks, and a user can retry a failed reading. Each was re-read and each replay is a no-op.

| Path | Guard | Verdict |
|---|---|---|
| Reading refund (`CreditsService.refundReadingCredit`) | `updateMany WHERE refunded_at IS NULL AND credits_used > 0`, inside a tx | ✅ idempotent + race-safe |
| Comparison refund (`refundComparisonCredit`) | same guard, **plus** clears `paidAt` and nulls `aiInterpretation` | ✅ — and correctly revokes access, not just money |
| Chat message refund (`ChatPaymentService.refundLastMessage`) | `updateMany WHERE refunded_at IS NULL` on the message; both sub-branches guard `> 0` before decrementing | ✅ — all four call sites converge on this one helper |
| Chat tier-upgrade stranded refund (`refundStrandedPaidOnTierChange`) | optimistic-concurrency check on `(paidMessagesUsed, creditExtensions)`; sets `paidMessagesUsed = creditExtensions * 10` | ✅ — a second tier change computes `refundable = 0` and skips |
| RC consumable clawback (`handleCancellation`) | UNIQUE `Transaction.stripePaymentId = rc-refund:<txid>` created **before** the clawback; P2002 → skip | ✅ — DB-level, independent of the webhook's Redis dedup |
| RC consumable grant (`handleConsumablePurchase`) | same pattern with `rc-purchase:<txid>` | ✅ |
| `clawbackCredits` arithmetic | `GREATEST(credits - n, 0)` in one row-locked UPDATE, `LEAST` captures the true amount | ✅ can't go negative under concurrency |

Regression coverage: `test/refund-idempotency.spec.ts` (13). These drive the real guards against an in-memory store with conditional-update semantics, so a replay returns `refunded: false` because the service's own `WHERE` matched nothing.

> ⚠️ **The fake's reads return a snapshot, not the live row — that detail is load-bearing.** With a live reference, a racing caller's write retroactively changed what an earlier reader saw, so the cheap pre-read appeared to stop the double-refund and the atomic guard was never exercised: deleting the guard entirely still passed. Caught by mutation. Three mutations now produce specific failures — removing the reading guard fails the concurrency test, removing the message guard fails the converging-callers test, removing `paidAt: null` fails the access-revocation test.

### A6-adjacent: credit movements that bypassed `CreditLedger`

A sweep of every `credits: { increment | decrement }` and absolute `credits:` write turned up three sites outside the ledger. `sum(CreditLedger.amount)` is supposed to reconcile against `user.credits`; each of these silently broke that.

| Site | Status |
|---|---|
| `admin.service.ts::adjustUserCredits` | ✅ **FIXED** — see A7 |

## A7 — admin money ops ✅ FIXED

`PATCH /api/admin/users/:id/credits` mints or removes real value. Auth is sound (`AdminGuard` → Clerk `publicMetadata.role`, 60s cache, fail-closed; `ClerkAuthGuard` is a global `APP_GUARD` so `request.auth` is verified before it runs). Two defects in the handler itself:

## F5 — fortune subscription window on the AI-chat door ✅ FIXED

**The hole.** The fortune HTTP routes enforce a window: FREE sees only the current period, paid tiers see −1 period back and +30 days / +12 months / +4 years forward. AI chat is a SECOND door onto the same engine output, and it validated profile ownership and the scope enum and nothing else. A FREE user created a session with `fortuneAnchorDate: "2030-01-01"`, spent 1 credit to extend, and had the AI narrate a 年運 that `GET /api/fortune/yearly?year=2030` refuses with 403. Worse commercially: a subscriber read **any** year at **zero** marginal cost, out of their monthly free-message quota rather than the +4yr window.

**Root cause is the shape, not the missing `if`.** The rule had one implementation reachable from one door. Patching only the chat call site would have left that shape intact.

**Fix.**
- `src/fortune/fortune-window.ts` (NEW) owns `FORTUNE_WINDOWS` + `assertFortuneWindow`. The three HTTP gates delegate to it; the six window constants in `fortune-snapshot.helpers.ts` are re-exports of that spec, so the *numbers* cannot drift either.
- Four chat doors enforce it: `createSession` (fail fast — no row), `sendMessage`, the SSE stream path, and `extendSession` (don't sell 10 messages every send will refuse — the same reasoning as the drift check beside it).
- `getChatContextForFortune` takes a **required** `userId` and lost its parameter defaults, so a call site that forgets the gate is a compile error. Both existing call sites were found that way. It runs before the profile lookup, cache read and engine call — a refused request costs nothing.
- Fails closed on a malformed anchor, in two layers: a per-scope shape regex, then a `Number.isFinite` backstop. Both are load-bearing — `2026-13-45` passes the DAY shape check and still yields `NaN`, and `NaN` satisfies neither `<` nor `>`.

**The per-message check is the load-bearing one.** The anchor is pinned on the session row, so a subscriber can open a +4yr session and then downgrade; gating only create would leave it serving content the tier no longer covers. Mirrors the comparison path's mid-session `paidAt` re-check.

**Behaviour change, bounded.** A FREE session spanning a period rollover now stops at the boundary rather than at the 24h session expiry — at most a few hours, and the content is exactly what the HTTP route refuses. Subscribers are unaffected (their −1 period past window covers it).

- **Lint ratchet**: `apps/api/eslint-suppressions.json` records per-file violation *counts*. Adding one new `any` to a file at its budget un-suppresses **every** violation in that file, so lint failures can appear on lines you never touched. Fix = don't add the violation (`as unknown as T`), not raise the budget. Cost me a detour; documented so it doesn't cost the next person one.
- **Verification hygiene**: `cmd | tail` returns *tail's* exit code. Capture the real exit before piping, or a failing check reads as passing. This produced one wrong "baseline is clean" conclusion mid-audit before it was caught.
- **A suite that fails to *compile* reports zero tests, and the headline number just gets smaller.** Adding a constructor arg to `AdminService` broke two admin specs at the TS level; `tsc -p tsconfig.json` didn't catch it (tests aren't in that project) and jest showed "1375 passed" with no failing *test*. Always read `Test Suites:` alongside `Tests:`, and reconcile the total against the expected baseline + new tests — here 1416 + 25 = 1441, which is what it should have been.
- **Mocks must match the shape the ORM returns, including snapshot semantics.** A fake that hands back the live row object lets a later write change what an earlier read saw — the opposite of a real query — which can make a concurrency test pass against code with the guard deleted. See the A6 note. The same class of error: writing `undefined` as if it were a value, when Prisma reads it as "don't update this column".
- **Establish reachability from the state machine, not from field names.** The F11 regression came from defending against a state (`isDegraded && refundedAt`) that the generator cannot produce, and the test written to defend it hand-built exactly that impossible row. Before adding a guard, ask which code path writes the state it guards against.
- **Where you inject a simulated race decides whether the test discriminates.** Injecting a concurrent spend at a read the code under test doesn't reuse leaves both the buggy and the fixed implementation landing on the same number. Hook the statement whose atomicity is the actual claim.
- **A mock cannot validate SQL.** Any correctness that lives in a raw query (`GREATEST`, `LEAST`, `ON CONFLICT`, CTEs) is untestable with a fake `$queryRaw` — the fake just replays whatever answer it was told to. Either write an integration test or say plainly in the test name what is and isn't covered.
